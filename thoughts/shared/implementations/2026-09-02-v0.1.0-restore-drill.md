# v0.1.0 — release tag and isolated restore drill

Closes the release-tag half of go-live **O2** outright, and the restore-drill
half for everything that is not a Fly resource. What is *not* covered is listed
under "Not covered" rather than implied to be done.

## The tag

`v0.1.0`, annotated, at `cc86bfb`. **The first tag in this repository** — zero
existed before, which is why the box stayed open: a restore drill against an
unnamed commit proves the procedure but not the release, because there is no
named thing to restore *to*.

It names: control plane on Fly (`abrolia-control-plane-synthetic`) plus landing
on Vercel, both shipped by `deploy-production` from green `main`; schema at
`0016_boot_archive_outcome.sql`; synthetic-only, with every `ABROLIA_REAL_*` at
`0` and canon Phase A's legal gate still open.

## What was drilled

`docs/control-plane-restore.md` § "Isolated restore rehearsal", steps 3–8,
against a database at the **current Phase E schema** — the thing the box
actually asks about, since the last drill predates `channel_preferences`,
`channel_bindings` and the usage tables.

The database was seeded through the **real repositories**, not hand-written
`INSERT`s. Rows a script invents prove the archive round-trips those rows, not
that the schema the service actually writes can be restored.

### The checks

1. **Pause marker** — mode `0600` before the snapshot.
2. **Archive** — real `abrolia-control-plane backup`, exit 0.
3. **Restore to a new path** — real `abrolia-control-plane restore --target`,
   never over the only copy.
4. **Verification** — `PRAGMA integrity_check` = `ok`; `foreign_key_check`
   zero violations; journal mode `wal`; migration ledger 16 deep with the
   expected newest entry.
5. **Row counts** — identical across all 27 tables, compared table by table
   rather than in aggregate.
6. **Phase E surfaces by content, not just count** — two `web` channel
   bindings, two `channel_preferences` rows with `primary_channel = web`, the
   `boot_archive_attempts` ledger, and two distinct `household_id`s so
   cross-household isolation is preserved through the restore.
7. **A restore refuses** — an existing target, a wrong backup key, a tampered
   archive (AES-GCM tag), and a corrupt file. All four rejected.
8. **Smoke without leasing** — with workers still paused: onboarding snapshot
   readable, export produced 21 tables, and **no `auth_tokens`, `sessions` or
   `bootstrap_tokens` hash appears in the export**, compared against the
   actual stored hashes rather than a pattern.
9. **`resume-jobs`** — workers resume only on the explicit command, never
   implicitly.
10. **A NEW onboarding reaches revision 1 on the restored database** — profile,
    email, WhatsApp and primary-channel steps, driven through the worker to
    `config_revisions.revision = 1`. Row counts prove an archive round-trips;
    this proves the restored database is still a working control plane.

### Two properties the drill tripped over, which is the point

- **The backup key must be independent of the application keys.** The first
  attempt set both from the same bytes and `ControlPlaneConfig.validate`
  refused: *"backup key must be independent from application keys"*. Recorded
  because a drill that never trips a guard has not exercised one.
- **Onboarding steps cannot be skipped or reordered.** The first attempt at
  step 10 selected the email step without saving the profile, and
  `InvalidTransition` refused it on the restored database exactly as it would
  on a fresh one.

## Not covered — remains operator work

Rehearsal steps 1–2 and the tail of step 8 need Fly resources and credentials
this drill did not have:

- attaching a **new isolated volume to a staging Machine** with no public route
  and no real-provider flags;
- restoring the **actual production archive** rather than an equivalent
  database at the same schema;
- **destroying the exact isolated staging resources** afterwards.

Also not exercised: **step 6's job reconciliation** against provider refs. The
seeded jobs were `pending`; no `running` or `outcome_unknown` job existed to
reconcile, so that path is untested here and stays part of the staging run.

What this drill establishes is that **the v0.1.0 schema, archive format and
restore path are sound, and a restored database is serviceable**. What it does
not establish is that the production volume restores onto a fresh Machine —
that is an environment question, and it is the remainder of O2.

## Reproducing

The drill scripts are not committed: they build a database, not a
verifiable artifact, and a committed script that is not run is not evidence.
The procedure is `docs/control-plane-restore.md` § "Isolated restore
rehearsal"; every command above is from it.

Note for whoever runs the staging half: `flyctl ssh console -C` **execs
directly** and will not accept `;` separators — wrap multi-command invocations
in `sh -c '…'`.
