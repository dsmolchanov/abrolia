# Contributing

Репозиторий публичный, а система работает с письмами школ, детскими данными и
секретами домохозяйств. Отсюда правила, которые важнее стиля кода.

## 1. Донорские фикстуры не копируются as-is

Код портируется из приватных доноров (`hermes`, `nerve-cloud`, `nerve-oss`;
ревизии — в [`docs/source-pins.md`](docs/source-pins.md)). Их тестовые payload'ы
содержат реальные Telegram ID, имена и адреса.

Переносится **структура** теста, а не значения: все идентификаторы, адреса,
телефоны и имена переписываются по конвенциям
[`tests/fixtures/README.md`](tests/fixtures/README.md). Если тест невозможно
переписать без реальных данных — он не переносится, вместо него пишется новый.

## 2. Санитайзер и секреты

```bash
export HERMES_EXTRA_DENY_FILE=~/.config/hermes-cloud/deny-patterns.txt
python3 scripts/check_fixtures.py --all --require-deny   # то же, что в CI
gitleaks detect --source . --config .gitleaks.toml --log-opts="--all" --redact
```

Версия gitleaks в CI закреплена (`.github/workflows/ci.yml`). Набор правил по
умолчанию меняется между релизами, поэтому «зелено локально» ничего не значит,
если локальная версия другая: изменения в `.gitleaks.toml` проверяются на
закреплённой версии, а её подъём — отдельным коммитом с прогоном по всей
истории.

Оба гоняются в CI на каждый PR: санитайзер — по всему дереву (`--all`), gitleaks
— по всей истории. Приватные deny-паттерны (реальные имена и ID донора, которые
нельзя держать в публичном репозитории даже как правило) приходят из секрета
`HERMES_DENY_PATTERNS`; без него шаг падает — гейт fail-closed, а не «прошёл
молча».

Правила исключений:

- `.check-fixtures-allow` — формат `путь | правило | точное значение`. Снимается
  ровно одна находка: то же значение в другом файле или другое нарушение на той
  же строке остаются видимыми.
- Приватные deny-паттерны (`custom`) исключить нельзя — загрузка такого файла
  считается ошибкой.
- В gitleaks нет исключений по путям: файл, исключённый целиком, — слепая зона.
- Запрещённые образцы в тестах собираются из кусков в коде (`joined(...)`),
  а не пишутся литералом — тогда исключения не нужны вовсе.
- Исключение ради «быстрее пройти CI» — повод отклонить PR.

Непроверяемый файл (картинка, PDF, аудио, база, не-UTF-8, больше 2 МБ) обязан
быть описан в `PROVENANCE.md` ближайшего родительского каталога — для фикстур
это `tests/fixtures/PROVENANCE.md`. Иначе санитайзер падает с правилом
`unscannable`: файл, содержимое которого никто не проверял, — слепая зона.
То же относится к отдельному вложению внутри `.eml`: оно описывается по своему
имени, а запись о письме его не покрывает (иначе одно бинарное вложение прятало
бы всё письмо).

Если реальный секрет всё же попал в историю: сначала ротация секрета у
провайдера, потом переписывание истории. Ротация — обязательна и первична.

## 3. Данные и приватность

- Логи не содержат содержимого писем и сообщений — только ID, статусы, размеры.
- Новый класс данных или новое место хранения → строка в
  [`docs/privacy/data-map.md`](docs/privacy/data-map.md) с TTL **в том же PR**.
- Новый внешний сервис → строка в
  [`docs/privacy/processors.md`](docs/privacy/processors.md) со статусом DPA/SCC
  **до** первого вызова из кода.
- Новое исходящее действие (email, сообщение, запись в календарь) → staged
  approval; ни одно наружное действие не исполняется без явного подтверждения
  человека (см. [`docs/SECURITY.md`](docs/SECURITY.md)).

## 4. Порядок работ

Канонический план — `thoughts/shared/plans/2026-08-02-family-ops-assistant-mvp.md`.
Фазы закрываются по порядку; критерии фазы — в самом плане. Реальные данные
семей не попадают в систему до закрытия Gate −1 и Фазы 2.

## 5. Стиль

- Python 3.12, `ruff check .` зелёный.
- Тесты — `pytest`; всё, что ходит во внешние API, помечается `@pytest.mark.live`
  и не идёт в обычном CI.
- Комментарии объясняют «почему», а не «что».
